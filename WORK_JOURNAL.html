01

專案概況

這是一套整合日常工作、財務、娛樂紀錄、天氣資訊的個人資訊管理網站。原始介面以《Star Trek》LCARS 為基礎；ui-redesign 分支目前採暖灰與朱紅的呈報簿介面。首頁以人物選擇、資料呈報及 TO DO LIST 組成，其他主頁顯示對應人物對話。摘要依既有資料在本機產生。

目前分支的介面與功能以本頁「目前 UI／UX 設計規範」及最新更新紀錄為準；「專案接手基線」保留 2026.09.18 的歷史盤點。新版增加 css/redesign.css 與 js/briefing.js，主網站目前有 11 個本機 JavaScript 檔案。

UX

目前 UI／UX 設計規範

適用分支：ui-redesign。2026.10.20 依使用者回饋重新定義。網站是需要反覆查看與操作的個人資訊管理工具，設計目標是快速理解狀況、找到下一步、完成後回到原來位置。介面不以品牌展示、刊物裝飾或儀表板卡片數量作為設計目標。

執行或深入處理「查看工作／財務／賽況／影劇與閱讀」操作名稱說明目的地，不使用四個完全相同而無法辨識的「查看詳情」。
隨手記錄首頁 TO DO LIST沿用同一份便箋資料與儲存鍵；完成項目不觸發提醒。其他主頁不顯示便箋抽屜。

視覺規則

  • 全站採系統無襯線字體，不依賴外部字體載入；正文 16px、一般輔助資訊 14px；表格欄名、行情日期、狀態與來源等緊湊資訊採 12–13px。全頁共用單一 H1（桌面 24px、手機 22px），區域標題約 19–20px，使用字重與間距建立層級。
  • 正文行高約 1.7，長文字限制閱讀寬度；主要區域以 8／16／24／32px 間距對齊。一般控制項至少 44px 高，卡片內次要按鈕約 38–40px，觸控裝置擴至 44px。鍵盤操作有清楚焦點框。
  • 依使用者選定的第三版「呈報簿」，預設採暖灰 #f6f2ec、米白 #fffcf7、朱紅 #a44d43 與深灰棕文字 #463b36。上方導覽維持淺色，選取人物使用朱紅側線與淡色底。警示搭配說明文字；配色固定使用目前版本，已移除舊主題切換。
  • 首頁不使用大型日期章、雙語品牌標語、裝飾英文標籤、拼貼式多尺寸卡片與各區不同的襯線標題。分隔線只標示資訊邊界，不讓每段文字都多包一層容器。
  • 共用視覺變數包括 --ui-line、--ui-soft、--ui-radius、--ui-radius-sm 與 --ui-shadow。主卡片採 10px 圓角、細框及輕陰影，內部控制採 6px 圓角；各主頁次級分頁統一朱紅底線與淡色選取，篩選按鈕使用較低層級。搜尋框只有一層邊框；行情漲跌採低彩度語意色，不使用深色標籤或螢光效果。
  • 圖示搭配文字；五位原創人物使用本機 images/advisors/council-five-cel.png 圓形頭像。桌面人物列位於首頁左側，手機改為五人橫向排列。主工作區上限 1440px；首頁右側為 TO DO LIST，其他主頁右側為相應人物對話，窄版改為單欄。戰績表在桌面固定美聯三欄在上、國聯三欄在下，較窄尺寸改兩欄或單欄。

互動、資料狀態與驗證

  • 載入時顯示「更新中」，停用重複更新；無資料與已知更新失敗使用不同文案，不把空清單直接當成錯誤。上次檢查時間是請求完成時間，不宣稱所有報價都在該時間更新。
  • 資料與觀察展開狀態、任務展開狀態及篩選選擇在重新渲染時保留；鍵盤焦點回到對應的操作。正在編輯便箋時不重建便箋 DOM。
  • 數據只從既有模組狀態讀取，缺資料不補造數字。保留原 API、儲存鍵與資料格式，使用隔離測試資料驗證，不測寫真實財務或個人紀錄。
  • 驗收包括：已載入／空資料／失敗、長標題、資料轉義、桌面與手機、文字實際字級、一般文字與背景對比、觸控尺寸、鍵盤焦點、各領域入口與便箋保存。

系統架構

介面層index.html、css/redesign.css
頁面骨架、樣式、SVG 圖示與響應式配置
核心協調層js/core.js、js/briefing.js
語言、導覽、快取、首頁呈報與人物對話
功能模組層js/*.js
專案、出勤、財務、比分、媒體、天氣及便箋
資料服務層Apps Script、Google Sheets、外部 API、localStorage 與 sessionStorage
  • 網站沒有前端框架、套件管理或編譯步驟，直接開啟 index.html 即可執行。
  • 所有 JavaScript 都是傳統腳本，共用全域作用域；載入順序及函式名稱具有相依性。
  • core.js 提供 t()、beep()、cacheGet()、cacheSet() 與主頁切換等共用能力。
  • switchPage() 依 .page[data-page] 與 .tab-btn[data-tab] 切換頁面，沒有 URL router；次級分頁分別由 setWsSubtab()、setLibSubtab()、setObsSubtab() 與 setFinanceTab() 控制。
  • 事件處理混用 HTML inline handler、元素的 onclick 及 addEventListener()，調整 selector 前需搜尋所有呼叫位置。
  • scores.js 的 escapeHtml()／escapeAttr() 被媒體模組使用；notes.js 的 overlay、prompt 與 confirm 被多個模組共用。
  • project.js 另有同名 closeOverlay()，會在淡出後呼叫 notes.js 留下的 window._overlayClose；不能將其中一個版本直接當成無用重複程式刪除。
  • 出勤模組沿用 proj-modal-* 樣式；影集、電影、閱讀共用 lib-* 樣式。調整共用 CSS 時需檢查所有使用端。
  • 啟動時會抓取金融、比分、排名及首頁天氣，其他資料部分按頁面造訪延遲讀取；比分計時器目前不會因離開 SCORES 頁面而停止。
  • 封面圖片放在 images/posters/，人物圖集放在 images/advisors/，歷史版本壓縮檔放在 _versions/。
目前腳本載入順序： finance → scores → notes → library → films → reading → attendance → project → weather → core → briefing。
04

功能特色

MAIN · 首頁呈報

五位人物依既有資料呈報工作、財務、賽事、影劇閱讀與天氣；右側 TO DO LIST 管理便箋與完成狀態。

WORKSPACE · 工作區

以 Project → Milestone → Task 管理專案，提供看板、優先順序、期限、模板；另有休假與加班紀錄。

FINANCE · 財務

顯示台美股、基金與匯率，支援自訂投資分頁、持倉資料、資產配置堆疊圖與 treemap。

SCORES · 賽事

讀取 MLB 比分與排名，預設聚焦 Baltimore Orioles，包含逐局資訊、賽況與自動更新。

LIBRARY · 媒體庫

記錄影集季／集進度、電影與重看、書籍閱讀與評分，提供搜尋、篩選及本機海報。

OBSERVATORY · 觀測站

台灣縣市天氣、逐時與逐日預報及日照資訊。

NOTES · 首頁待辦

首頁 TO DO LIST 支援新增、編輯、排序、顏色、到期提醒及完成勾選；資料保存在目前瀏覽器。

呈報簿 UI

暖灰與朱紅配色、上方導覽、五人原創圓形頭像、SVG 圖示及中英文切換。

RESPONSIVE

桌面首頁顯示人物、呈報與待辦；其他主頁顯示功能內容與人物對話。窄版改為單欄。

設計與維護原則

開始工作前

  1. 先閱讀本工作手記。
  2. 查看專案目錄與 git status。
  3. 必要時查看最近的 git log 與相關 commit。
  4. 若有 HANDOFF.md 或 TODO.md，先閱讀再修改。
  5. 若其他電腦最近有新修改，先理解變更內容。

程式修改

  • 採取最小必要變更，優先修改現有檔案。
  • 不任意更換框架、函式庫或建置方式。
  • 不新增不必要的相依套件。
  • 修改函式前先確認所有呼叫位置。
  • 範圍外的舊問題先記錄，不順手大改。

UI / UX

  • 未經明確要求，不改變頁面配置、操作流程、導覽方式、按鈕位置或響應式行為。
  • 沿用目前呈報簿設計語言及既有程式命名。
  • 桌機與手機版須交叉檢查。
  • 跨頁調整前先確認共用元件與共用樣式。

JavaScript

  • 先找出事件監聽、DOM selector、共用函式、資料來源及瀏覽器儲存。
  • 不任意重新命名函式、DOM ID 或 class。
  • 新增功能應整合進現有架構，避免平行重複邏輯。
  • 資料格式變更須同步檢查讀寫及所有使用端。

CSS

  • 優先修改現有 class，避免大量重複樣式。
  • 注意 selector specificity。
  • 沿用既有 responsive breakpoint。
  • 不為單一畫面問題大量使用 !important。

Git 與檔案安全

  • 保留未提交修改，不覆蓋或丟棄使用者內容。
  • 未經明確要求，不執行 commit、push、pull、merge、rebase、reset，亦不建立或切換 branch。
  • 不刪除用途未確認的檔案或大量既有程式碼。
  • 不因程式可以更漂亮而重做整個網站。
核心原則：先理解現有專案，再修改；優先維持既有功能與使用者操作方式；採用最小必要變更，避免非必要重構。

完成工作後的固定回報

  1. 修改了哪些檔案，以及每個檔案的主要變更。
  2. 是否可能影響其他功能或共用元件。
  3. 建議使用者測試哪些項目。
  4. 若適合，提供簡潔明確的 Git commit message，但不自行提交。
  5. 在本頁更新紀錄留下日期、行為變更、影響範圍與驗證結果。
